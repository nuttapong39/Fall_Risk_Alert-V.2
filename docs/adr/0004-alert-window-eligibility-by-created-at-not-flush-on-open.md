# Alert Window ตัดสินด้วย created_at ต่อแถว ไม่ใช่ flush ทั้ง backlog ตอนหน้าต่างเปิด

ADR-0003 ออกแบบให้ Alert Window เป็น "buffer แล้ว flush ทีเดียว": นอกช่วงเวลา `had_queue`
สะสมเป็น Pending ไปเรื่อย ๆ พอนาฬิกาเข้าสู่ช่วงเวลาที่ตั้งไว้ **ทุกแถวที่ Pending ค้างอยู่**
(ไม่ว่าจะมาจากตอนไหน) จะถูกส่งออกทีเดียว — ห้องยายืนยันว่านี่ไม่ใช่พฤติกรรมที่ต้องการจริง
ความตั้งใจจริงคือ **auto-send เฉพาะแถวที่ "เกิด" ในช่วงเวลาที่ตั้งไว้เท่านั้น** ส่วนแถวที่เกิด
นอกช่วง ต้องพัก Pending ตลอดไปแม้หน้าต่างจะเปิดในรอบถัดไปก็ตาม จะส่งได้ต้องสั่งเองทางปุ่ม
"ส่งซ้ำทันที" เท่านั้น (grill session, 2026-09-23)

เราใช้ `created_at` (เวลาที่ Ingest เขียนแถวลง `had_queue`) เป็นตัวตัดสิน "แถวนี้เกิดตอนไหน"
— เป็นคอลัมน์เดียวที่มี time-of-day ละเอียดพอและมี index `idx_status_created(status,
created_at)` รองรับอยู่แล้ว (`vstdate` เป็นแค่ `date` ไม่มีเวลา)

## Considered Options

- **กรองด้วย `created_at` ที่ SQL `WHERE` ของ `had_send_pending()` (เลือก)** — เทียบ
  `TIME(created_at)` กับช่วง start/end แบบเดียวกับที่ `alert_window_is_open()` เทียบ "ตอนนี้"
  อยู่แล้ว (ครอบคลุมเคสข้ามเที่ยงคืนแบบเดียวกัน) กันปัญหา starvation ที่แถว Pending เก่า (id
  น้อย นอกช่วง) จะบัง `ORDER BY id ASC LIMIT 50` ไว้ตลอดจนแถวใหม่ในช่วงเวลาไม่มีวันถูกดึงมาส่ง
  ถ้ากรองทีหลังใน PHP หลัง fetch — ADR-0003 เคยปฏิเสธ "กั้นในฐานข้อมูล" ไว้ด้วยเหตุผลเรื่อง log
  ไม่บอกสาเหตุ + ผูก dialect โดยไม่จำเป็น แต่ทั้งสองข้อไม่กระทบที่นี่: log เหตุผลยังทำได้ที่ระดับ
  worker เหมือนเดิม (ไม่ได้ซ่อนนโยบายทั้งหมดไว้ใน SQL แค่กรองว่าแถวไหนเข้าเกณฑ์) และ
  `MedAlert_DB` เป็น MySQL เสมอไม่มีทาง dialect อื่น (work-flow.md §1) จึงไม่ใช่ปัญหาเดิม
- **กรองใน PHP หลัง fetch 50 แถวแรก** — **ปฏิเสธ**: เจอ starvation จริงตามที่อธิบายข้างต้น
- **ให้ Re-queue รีเซ็ต `created_at` เป็นเวลาปัจจุบัน แล้วปล่อยให้กฎเดิมตัดสิน** — **ปฏิเสธ**:
  ห้องยาเลือกตัดปุ่ม/action "Re-queue" ออกจาก HAD ไปเลยแทน (ดู Consequences)

## Consequences

- **มีผลย้อนกับ backlog เดิมทันทีที่ deploy** — แถว Pending เก่าที่ `created_at` (เทียบแค่
  เวลาของวัน ไม่สนวันที่ — เหมือน `alert_window_is_open()` เดิม) ตกอยู่ในช่วงเวลา จะถูกส่งออก
  ในรอบ cron ถัดไปที่หน้าต่างเปิด ทันทีที่ deploy โดยไม่ต้อง migrate พิเศษ — ตรงตาม intent เดิม
  ("ควรถูกส่งไปนานแล้วแต่ยังไม่ได้ส่ง") ไม่ใช่ผลข้างเคียง
- **ตัดปุ่ม/action "Re-queue" ออกจาก HAD โดยเฉพาะ** (`had_queue_ui.php`,
  `had_queue_action.php`) — เดิม Re-queue แค่ reset `status=0, attempt=0` ไม่แตะ `created_at`
  เลย ถ้าใช้กับแถวนอกช่วงจะกลายเป็นปุ่มที่กดแล้วไม่มีผล (ค้าง Pending ตลอดไปเหมือนเดิม เพราะ
  `created_at` เดิมยังตกนอกช่วงอยู่) ตัดออกเพื่อไม่ให้เข้าใจผิดว่ากดแล้วจะส่งได้ — เหลือ
  "ส่งซ้ำทันที" (`had_send_one()`) เป็นทางแมนนวลทางเดียว ซึ่งไม่เช็คทั้ง cooldown และ maxTry
  อยู่แล้ว จึงไม่มีช่องโหว่ (แถวที่พังถาวรเกิน maxTry ยังกู้คืนได้ปกติ) โมดูลอื่นไม่กระทบ
  (Re-queue ทั่วไปยังทำงานตามเดิมตาม work-flow.md §3)
- **ข้อความ UI/log ที่อ้างว่า backlog จะ "ไหลออกเมื่อหน้าต่างเปิด" ต้องแก้ทั้งหมด** —
  `HAD.php` (SKIP SEND log), `had_queue_ui.php` (modal ช่วงเวลาแจ้งเตือน) เคยบอกว่าคิวจะไหล
  ออกทีเดียวตอนหน้าต่างเปิด ซึ่งไม่จริงอีกต่อไป
- **ความจุ/ความเสี่ยงคิวล้นตาม ADR-0003 ลดความสำคัญลง** — เพราะไม่ต้องระบาย backlog ทั้งวัน
  ออกในหน้าต่างเดียวอีกต่อไป (แถวกระจายส่งตามเวลาที่เกิดจริงภายในช่วง) ตัวคำนวณ capacity ใน
  modal (`AW_SEND_LIMIT`/`AW_CRON_MIN`) ยังถูกต้องเป็น ballpark แต่ความเร่งด่วนของคำเตือนสีแดง/
  ส้มลดลง — ไม่ได้แก้ตัวเลขในงานนี้
- fail-open, default ปิด, และตรรกะข้ามเที่ยงคืนของ `alert_window_is_open()`/`alert_window()`
  ไม่เปลี่ยน — ยังใช้ตัดสิน "ตอนนี้อยู่ในช่วงไหม" (gate ของทั้ง worker) เหมือนเดิมทุกประการ
  ส่วนที่เพิ่มคือชั้นกรองต่อแถวซ้อนขึ้นมาอีกชั้นหนึ่งเท่านั้น
